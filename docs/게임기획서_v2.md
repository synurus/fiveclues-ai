# 다섯고개 — 기획서 v2

작성 2026-09-15. v1(2026-09-14)을 대체한다.
v1의 "사람 1 + 봇 다수 / 봇이 라이어를 투표" 구조는 폐기했다. 이 문서가 현행 설계다.

---

## 0. 프로젝트 핵심

**게임성 + 봇 프롬프트 엔지니어링.** 모든 설계 판단은 이 둘을 기준으로 내린다.

---

## 1. 한 줄 정의

> **AI의 묘사를 통해 제시어를 맞추는 게임.**

플레이어는 AI가 내놓는 묘사 5개를 보고 제시어를 추측한다. 틀리면 묘사 5개를 더 받고
한 번 더 추측한다. 판이 끝나면 **어떤 묘사가 결정적이었고 어떤 묘사가 쓸모없었는지**를
고른다 — 그 선택이 다음 판의 묘사를 바꾸고, 동시에 프롬프트 개선의 학습 신호가 된다.

---

## 2. v1에서 바뀐 것

| | v1 | v2 |
| --- | --- | --- |
| 구조 | 사람 1 + 봇 5, 봇이 라이어 투표 | **봇 1개가 묘사만 생성** |
| 숨기기 | 사람이 라이어로 잠입 | **없음** — 순수 추측 게임 |
| 봇 호출 | 판당 16회 (봇마다 개별 호출) | **판당 2~3회** (한 번에 묘사 5개) |
| 학습 신호 | 봇 투표 + 사람 지목 | **결정적 / 무쓸모 (사람이 직접, 양방향)** |
| 제시어 | 12주제 × 8단어, 주제 공개 | **주제 없이 200개 풀, 계속 추가** |

**왜 단순해졌는가**: v1의 봇 투표는 "사람이 무엇을 누출로 느끼는가"의 노이즈 낀 대리
지표였다. v2의 결정적/무쓸모 선택은 그 판단을 사람에게서 직접 받는다. 대리 지표가
필요 없어지면서 봇 5마리와 투표 구조 전체가 불필요해졌다.

---

## 3. 게임 흐름

```
입장         닉네임 또는 ID 입력
1라운드      AI 묘사 5개 (타이핑하듯 순차 렌더)
1차 추측     제시어 입력
  ├ 정답 → 결과 「참 잘했어요」
  └ 오답 ↓
2라운드      AI 묘사 5개 (1라운드와 겹치지 않게, 더 구체적으로)
2차 추측     제시어 입력
  ├ 정답 → 결과 「잘했어요」
  └ 오답 → 결과 (정답 공개)
라벨         결정적 힌트 선택 / 무쓸모 힌트 선택 / 피드백(선택)
```

### 라운드 수 — 2라운드 + 정답 공개

3라운드는 두지 않는다. 묘사 10개를 보고도 못 맞히면 15개를 준다고 맞히지 않고,
"어차피 안 되겠네"가 된다. 대신 **실패해도 반드시 정답을 보여준다** — 정답을 모른 채로는
어느 묘사가 결정적이었는지 판단할 수 없어서 라벨이 무의미해진다.

### 결과 화면

| 조건 | 표시 |
| --- | --- |
| 1라운드 정답 | 「참 잘했어요」 도장 |
| 2라운드 정답 | 「잘했어요」 도장 |
| 실패 | 정답 공개 |

### 타이핑 렌더링

묘사를 한 번에 뿌리지 않고 실제로 입력하는 것처럼 한 글자·한 단어·한 문장씩 찍는다.

- 텍스트를 살아 있게 만드는 가장 싼 방법이고, **시연 영상에 볼 것을 만든다**
- 호출 대기(3~8초)를 기대감으로 바꾼다 — 이미 받아둔 텍스트를 뿌리는 것이므로
  **스트리밍 API가 필요 없다**
- 묘사가 하나씩 도착하는 리듬이 있어야 "다음 걸 보면 알 것 같다"는 긴장이 생긴다

---

## 4. 묘사 생성

### 한 번 호출로 5개를 받는다

봇을 5번 부르지 않는다. **이건 비용 문제가 아니라 제어 문제다.**

5번 나눠 부르면 각 묘사는 서로를 모른다. 한 번에 받으면 모델이 **세트 전체를 설계**할
수 있다 — 스타일이 겹치지 않게 배분하고, 난이도를 계단식으로 깔고, 정보량 총합을
조절하는 것이 프롬프트로 지시 가능해진다.

**최적화 단위는 묘사 하나가 아니라 묘사 세트다.**

### 스타일 태그

각 묘사에 스타일 태그를 달아 생성한다. 라벨을 다시 프롬프트로 되먹이려면
"무엇이 쓸모없었는가"를 태그 단위로 집계할 수 있어야 한다.

```
단답형   문장형   비유   용도·기능   감각(색/소리/촉감)   상황·맥락   부정형
```

JSON으로 받는다: `[{ "text": "...", "style": "비유" }, ...]`

### 2라운드는 1라운드보다 쉬워야 한다

"겹치지 않게"만으로는 부족하다. 2라운드 호출에 1라운드 묘사를 넣고 **난이도를 낮추라고
명시**한다. 안 그러면 애매한 묘사 5개가 더 나올 뿐이고, 플레이어는 두 배로 답답해진다.

---

## 5. 라벨 수집

판이 끝나면 세 가지를 묻는다.

| 라벨 | 의미 | 프롬프트 엔지니어링에서의 역할 |
| --- | --- | --- |
| **결정적 힌트** (없음 가능) | 제시어를 알아채게 만든 묘사 | 구체성 과다 페널티 |
| **무쓸모 힌트** (없음 가능) | 아무 정보도 없던 묘사 | 모호함 페널티 |
| **피드백** (선택) | 자유 서술 | 정성 신호 |

**양방향인 것이 핵심이다.** 누출만 벌주면 묘사가 한없이 모호해지고, 모호함만 벌주면
정답이 바로 새어나간다. 두 압력이 같이 있어야 중간 지대가 생긴다.

"없음" 옵션도 그 자체로 신호다 — 결정적 없음은 "세트가 전부 약했다",
무쓸모 없음은 "세트가 전부 쓸 만했다"를 뜻한다.

### ⚠️ 라벨링 피로 — 이 설계 최대의 리스크

**한 판 2분에 라벨을 3개 요구하고 있다.** 1~2판은 성실하게 하고, 5판째부터 대충 찍는다.
대충 찍은 라벨은 없느니만 못하다 — 노이즈가 섞인 데이터로 세대를 비교하면 잘못된
방향으로 확신을 갖게 된다.

**이 프로젝트의 프롬프트 엔지니어링 가치는 전부 이 라벨이 정직하다는 가정 위에 있다.**

대책:
1. **라벨을 다음 판에 반영한다** (6장) — 라벨링이 의무가 아니라 내 경험을 조종하는
   수단이 되면 성실하게 찍을 이유가 생긴다
2. **피드백 입력창은 선택으로 둔다** — 매 판 강제하면 셋 중 제일 먼저 버려지고,
   버려지기 시작하면 앞의 둘도 같이 대충 하게 된다
3. 라벨 화면은 **클릭 두 번으로 끝나게** 한다 — 묘사 카드를 그대로 누르는 방식

## 6. 즉시 적응 vs 세대 진화 — 두 축을 섞지 않는다

"한 판 끝나고 바로 다음 판에 프롬프트 개선을 적용할 수 있는가"에 대한 답.

### 축 A — 즉시 적응 (가능하다. 해야 한다)

플레이어별 스타일 가중치를 들고, 라벨에 따라 조금씩 움직인다.

```
무쓸모로 찍힌 스타일  → 가중치 ↓
결정적으로 찍힌 스타일 → 가중치 소폭 ↓ (너무 셌다는 뜻)
그 외                → 유지
```

다음 호출 프롬프트에 "이번엔 이런 스타일 위주로" 한 줄을 넣는 것으로 끝난다.
**비용 0, 즉각 반영, 플레이어가 체감한다.**

⚠️ **한 판의 라벨 1~2개로 크게 움직이면 과적합이다.** 우연히 찍힌 하나 때문에 스타일이
통째로 꺼질 수 있다. 가중치는 조금씩만 움직이고 **하한을 둔다(0으로 내리지 않는다)**.

### 축 B — 세대 진화 (판마다 하면 안 된다)

프롬프트 원문 자체를 고치는 것. 이건 **N판을 모아서 한 번** 한다.

매 판 프롬프트를 다시 쓰면 **세대 비교가 불가능해진다.** 지표가 판마다 다른 프롬프트를
재게 되어 아무것도 측정하지 못하고, 수십 판 뒤엔 프롬프트가 드리프트해서 무엇이
무엇인지 알 수 없게 된다.

- 세대당 최소 판수를 지킨다 (초기값 20판)
- 그 세대 동안 프롬프트는 **고정**
- 신뢰구간을 항상 같이 본다 — "1라운드 정답률 32% ± 11%"
- 자가대전에서 겪은 것과 같은 문제다: **양보다 다양성**

### ⚠️ 두 축을 섞으면 측정이 무너진다

축 A는 **플레이어별 상태**, 축 B는 **전역 프롬프트**다.

섞으면 "3세대가 좋아졌다"가 실은 "이 플레이어에게 적응했다"인 것을 구분할 수 없다.
**세대 비교용 판에서는 축 A를 끄거나**, 최소한 그 판의 가중치 상태를 기록해서
나중에 통제할 수 있게 한다.

## 7. 제시어 풀

### 주제(카테고리)를 플레이어에게 보여주지 않는다

기존에는 "동물 중 하나"를 알려줬다. 8개 중 하나라 너무 쉬웠다.

주제를 감추면:
- 첫 묘사가 **범주를 좁히는 역할**을 자연스럽게 맡게 되어 묘사 5개에 난이도 계단이 생긴다
- 봇이 "동물입니다" 같은 이미 아는 정보를 쓸 수 없게 된다
- 체감 난이도 상승은 생각보다 작다 — "네 발로 걷고 갈기가 있다"면 범주는 즉시 드러난다

### 200개로 늘리고 계속 추가한다

- 96개는 한 사람이 20판만 해도 겹치기 시작했다. **한 번 본 단어는 기억한다** —
  재미도 떨어지고 데이터도 오염된다
- 200개면 20판에 10%만 소진
- 플레이어별로 **본 단어를 기록해 제외**한다
- 단어 추가가 쉬워야 한다 (SQL 한 줄 또는 JSON 파일)

### 주제는 지우지 말고 내부 태그로 남긴다

**UI에서만 감추고 데이터에는 유지한다.** `categories` 테이블과 `words.category_id`를
그대로 두는 쪽이 낫다:

- "어떤 범주의 단어가 어려운가"를 분석할 수 있다
- 나중에 난이도 모드(주제 공개/비공개)를 넣을 여지가 남는다
- 스키마를 건드리지 않아도 된다

단어별 정답률이 쌓이면 **난이도 라벨이 자동으로 생긴다** — 추가 작업 없이 얻는 부수효과다.

## 8. 측정 지표

| 지표 | 정의 | 목표 |
| --- | --- | --- |
| **1라운드 정답률** | 묘사 5개로 맞힌 비율 | **25~35% 밴드** |
| **최종 정답률** | 2라운드까지 맞힌 비율 | 70~80% |
| **무쓸모율** | 전체 묘사 중 무쓸모로 찍힌 비율 | **최소화** |
| 결정적 힌트 분포 | 몇 번째 묘사가, 어떤 스타일이 결정적이었나 | 관찰용 |
| "없음" 비율 | 결정적 없음 / 무쓸모 없음 각각의 비율 | 관찰용 |

### 최적화 목표 한 줄

> **무쓸모율을 최소화하면서 1라운드 정답률을 목표 밴드에 머무르게 한다.**

정답률만 올리면 묘사가 노골적이 되고, 무쓸모율만 낮추면 전부 적당히 유용한 밋밋한
세트가 된다. 둘을 같이 봐야 한다.

### ⚠️ 플레이어 학습 효과를 프롬프트 개선으로 착각하지 말 것

같은 사람이 반복하면 요령이 생겨 정답률이 오른다. **판마다 플레이어 id와 그 사람의
누적 판수를 반드시 기록한다.** 세대를 비교할 때는 **초행 플레이어의 판만** 골라서 본다.

## 9. 데이터 스키마

기존 테이블을 거의 그대로 쓴다.

| 기존 | v2에서의 용도 |
| --- | --- |
| `game_messages` + `runtime_id` | 묘사 하나하나. `runtime_id`로 지목 대상이 된다 |
| `survey_responses.picked_message_runtime_id` | **결정적 힌트** 지목 |
| `games` · `words` · `categories` | 그대로. 카테고리는 내부 태그로 유지 |
| `games.bot_provider` · `bot_model` · `bot_commit_sha` | 세대 비교의 축 |
| `survey_responses.free_text` | 피드백 |

**신설이 필요한 것**

- 묘사의 **스타일 태그** (`game_messages`에 컬럼 추가)
- **무쓸모 힌트** 지목 (`picked_message_runtime_id`와 짝이 되는 컬럼)
- **세대 식별자** (프롬프트 버전)
- **플레이어 식별자와 누적 판수**
- 플레이어별 **출제 이력**(본 단어)

## 10. 기술

### 호출량

| | 판당 호출 | Groq 무료 1,000회/일 |
| --- | --- | --- |
| 1라운드만 (정답) | 1회 | 1,000판 |
| 2라운드까지 | 2회 | 500판 |

**호출량은 더 이상 제약이 아니다.** 라운드 수와 묘사 개수를 비용이 아니라 재미 기준으로
정할 수 있다.

- Groq 1순위(30 RPM · 카드 불필요 · 학습 미사용), Cerebras 대체
- Google AI Studio 제외 — EU/UK/EEA 밖은 프롬프트를 모델 개선에 사용한다고 명시
- 개발 중 대량 실행은 로컬 RTX 4090

### 배포

플레이어가 1명이고 실시간 상호작용이 없다. **WebSocket이 필요 없다** —
요청/응답 한 번에 묘사 5개를 받아오면 끝이다.

이전 설계의 배포 제약(300초 함수 제한, 인스턴스 간 브로드캐스트, 라운드 무한 루프)이
**전부 사라진다.** Vercel을 포함해 어디에 올려도 된다.

⚠️ `RAILWAY_GIT_COMMIT_SHA`는 `db/game.ts:51`에서 `games.bot_commit_sha`에 들어간다.
플랫폼을 옮기면 비어버려 세대 비교가 망가진다 — 플랫폼 중립 이름으로 교체할 것.

## 13. 함정

- **라벨링 피로가 데이터 품질을 무너뜨린다.** 5장 참고. 이 설계의 단일 최대 리스크.
- **한 판 라벨로 크게 조정하면 과적합.** 우연히 찍힌 하나로 스타일이 꺼진다.
- **즉시 적응과 세대 진화를 섞으면 측정이 무너진다.** 6장 참고.
- **플레이어 학습 효과를 프롬프트 개선으로 착각한다.** 초행 판만 비교할 것.
- **2라운드가 1라운드보다 안 쉬우면 라운드를 나눈 의미가 없다.**
- **정답을 안 보여주면 라벨이 무의미해진다.** 어느 묘사가 결정적이었는지 판단할 근거가 없다.
- **표본이 모자라면 좋아진 건지 운이 좋았던 건지 모른다.** 신뢰구간을 항상 같이 볼 것.
